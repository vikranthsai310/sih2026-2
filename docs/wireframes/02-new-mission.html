Why an anchor matters

Consumer drone GPS places the model a few metres off, but the error is mostly a rigid shift (the same offset everywhere). One good anchor, such as a reference orthophoto, DSM, RTK/PPK track or a single known point, removes most of it.

Shapes, lengths, areas and volumes (relative accuracy) are good either way. Anchoring changes where on Earth the model sits (absolute accuracy).

Source: Zhang et al. 2019 (vertical bias 3.93 m with 0.18 m spread). Details in docs 06 §1 and §11.

02 · New Mission

09 §5.2 · Persona: field operator · POST /api/v1/missions, POST /api/v1/uploads, PUT …/chunks/{n}, POST …/complete
  1. Stepper shows the mission pipeline (Inputs → Ingest check → Processing → Results). Upcoming steps are not clickable until their data exists.
  2. Video dropzone: chunked, resumable upload. The server probes the file (ffprobe). Pause keeps the received chunks; GET /api/v1/uploads/{id} lists them for resume.
  3. Telemetry is matched to the video by basename (case-insensitive). If there's no SRT/KLV, the primary becomes "Continue without GPS (relative model only)" with a red warning (see states).
  4. "What's this?" opens a short explainer the first time: anchoring removes the rigid GNSS bias.
  5. Profile defaults to fast. preview disables the 3D tabs for this run.
  6. Accuracy expectation is stated before processing, labelled as a target. The GNSS-only warning is shown when no anchor is supplied.
  7. Primary goes to the Ingest Check (S0 quick pass), never straight to processing (09 U1). Calls POST /api/v1/missions/{id}/ingest-check.
